# 任務：批文卡辨識（OCR）改進

你是實作工程師，技術負責人會逐項驗收，不合格會退回。

## 問題

用戶上傳批文卡後，部分欄位被讀成亂碼並直接顯示。負責人在本機用真實批文卡測試的結果：

| 欄位 | 正確內容 | 現在讀出 |
|---|---|---|
| 內地車牌 | 粵Z98B7港 | 锣77RA!D港 |
| 現批文號 | 2025第0633333号 | 门门门芭Am人-mr广己 |
| 原批文號 | 2024第0444444号 | 全人二DO0OD24人等mm4472站D呈 |
| 顏色 | 黑 | 人 |
| 請予辦理 | 延期 | 区期 |
| 駕駛人 1 | 张伟明 | 张伟名 |
| 駕駛人 3 | 黄志强 | （沒有讀） |
| 有效期 | 2025-11-27 至 2027-01-01 | 開始日被填成 2027-01-01，結束日空白 |
| 卡面流水號 | 00654321 | （空白） |

同一套程式讀另一張卡（大明 1088123）大致正確，所以問題主要不在圖片清晰度，而在辨識方法。

## 根本原因（負責人分析，請先核實）

1. **固定座標框**：`api/src/card.js` 把整張圖片硬拉成 1015×645，再用固定矩形讀每個欄位。上傳圖片的卡面周圍有白邊、比例不同、位置偏移，或者駕駛人有三位時下面各列往下移，框就會錯位。
2. **沒有裁出卡面**：沒有先找出卡片邊界，白邊也被一起拉伸。
3. **只用中文模型**：英數字（批文號、車牌、日期）用 `chi_sim` 讀錯率高。
4. **沒有前處理**：卡面淺藍底紋干擾文字。
5. **沒有驗證**：讀出甚麼就填甚麼，亂碼直接進入卡面資料。
6. **欄位遺漏**：背面矩形沒有 `driver3`。

## 要做的事

### A. 辨識流程（`api/src/card.js`，可拆模組）

1. **找出並裁切卡面**：偵測卡片邊界，去掉白邊；能做到的話校正輕微傾斜（±5°）。再縮放到模板尺寸。
2. **前處理**：灰階、放大（例如 2 倍）、對比正規化、銳化；壓低淺藍底紋（文字是深色，底紋是淺藍）。可以產生多個變體輪流嘗試。
3. **以標籤定位欄位**：先對整張卡做版面辨識，取得文字和位置，找出標籤（编号、商号、内承单位、通行口岸、内地车牌号、港澳车牌号、驾驶人、现批文号、原批文号、颜色、座位/吨位、请予办理、有效期、备注），再按標籤位置推算對應值的區域。找不到標籤時才退回模板座標。
4. **分欄位再辨識**：
   - 純數字欄位（编号、流水號）用數字白名單
   - 車牌、批文號、日期使用中英合用模型
   - 可以加入 Tesseract 官方的 `eng.traineddata`（從 `tesseract-ocr/tessdata_fast` 或 `tessdata` 取得），放在 `api/tessdata/`，在報告中寫明來源網址和 SHA-256。這是本任務允許的唯一新增檔案類型
5. **多候選取最佳**：每個欄位可以有多個候選結果（不同前處理、不同模式），選通過驗證且信心最高的一個。
6. **欄位驗證**（通不過就不填）：
   - 编号：6–8 位數字；卡面流水號：8 位數字
   - 內地車牌：`粵Z` + 4 位英數 + `港` 或 `澳`（OCR 讀出的「粤」轉為「粵」）
   - 港澳車牌：香港 1–8 位英數；澳門 `M` 開頭格式
   - 現批文號、原批文號：`YYYY第NNNNNNN号`
   - 有效期：兩個合法日期，開始早於結束
   - 顏色：常見車色單字或詞（黑、白、灰、銀、紅、藍、黃、綠、棕、金、紫、橙及其簡體）
   - 座位／噸位：`N座` 或噸位格式
   - 駕駛人：2–4 個漢字
   - 通行口岸：已知口岸名稱（大桥、深圳湾、莲塘、皇岗、落马洲、文锦渡、沙头角、拱北、横琴等）
   - 請予辦理：已知業務詞（延期、新办、换车、变更驾驶人等）
7. **交叉校正**：備註通常寫著「主司机:姓名(編號),副司机:…」，可用來校正或補齊駕駛人 1–3。
8. **絕不輸出亂碼**：驗證失敗的欄位回傳空字串，不覆蓋已有的值（現有上傳邏輯已過濾空值，保持這個行為）。
9. **效能**：重用同一個 Tesseract worker；單面辨識在本機應少於 15 秒。

### B. API 回傳

`recognizeCard` 除了欄位值，再回傳每個欄位的狀態：`{ value, status: 'ok' | 'uncertain' | 'failed', confidence }`。`/api/card-recognize` 和 `/api/plate-assets/:id/card/(front|back)` 的回應加上 `fieldStatus`。已有的 `cardData`、`recognized` 回傳格式不變，前端舊呼叫照常可用。

### C. 前端

- 管理端（`admin/src/App.vue` 的批文卡欄位表單）和客戶端（`mobile/src/pages/plate-create/`、`mobile/src/pages/plate-detail/`）：辨識後狀態為 `uncertain` 或 `failed` 的欄位，在**表單**旁顯示琥珀色「請核對」或「未能辨識，請手動填寫」
- **批文卡模擬卡的呈現效果不得改變**：不得修改兩個 `ApprovalCard.vue`；預覽、翻轉、疊層、版本選擇等交互保持原樣
- 本任務允許修改 `mobile/` 中上述兩個頁面，其他 `mobile/` 檔案不要動

### D. 測試

- `api/test/ocr.test.js`：
  - **真實樣本**（`api/test/fixtures/cards/`，含 `expected.json`）：若資料夾存在，逐欄比對，正規化後必須全部一致；資料夾不存在時跳過，並在輸出註明「未提供真實樣本」
  - **合成樣本**（必做，不依賴真實資料）：用 `sharp` 和 SVG 生成模擬批文卡正反面（欄位位置和字體大小參照 `admin/src/components/ApprovalCard.vue` 的版式），並產生劣化版本：高斯模糊（sigma 1.2）、縮小到 50%、JPEG 品質 40、旋轉 2°、四周加白邊並偏移。原圖要求全部欄位正確；劣化版要求至少 90% 欄位正確，且**任何非空欄位都必須通過驗證**（零亂碼）
- 單元測試覆蓋每個欄位的驗證和正規化函數
- `cd api && npm test`、`cd admin && npm run build`、`cd mobile && npm run build:h5` 都必須通過

## 限制

- 不新增 npm 依賴（`sharp`、`tesseract.js` 已有）；只可新增官方 `eng.traineddata`
- 不讀取或修改 `api/data/`、`data/`、任何 `*.sqlite`
- 不修改兩個 `ApprovalCard.vue`；不 commit
- 不要動第一階段的多租戶和規則程式碼，除非是為了接上 `fieldStatus`
