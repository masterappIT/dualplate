# 第一階段驗收：第 1 輪退回意見

日期：2026-10-16。結果：**不合格，退回修改。**

負責人已重跑 `npm test`（8 通過）和 `npm run build`（通過），並另行做了獨立探測測試和瀏覽器實測。批文卡區塊目前完好，租戶隔離的主要路徑正確。以下問題必須全部修正。

## 一、功能錯誤（必改）

1. **NAR1 在成立當年被判為到期**。你把 `anniversary` 的年份條件從 `y > base` 改成 `y >= base`，這是錯的。香港周年申報表是成立**周年日**後 42 天，成立當年沒有申報。探測結果：兩個月前成立的公司被列為 `overdue`，到期日是成立日加 42 天。請改回只計成立年之後的年份，並加測試：今年成立的公司，第一期到期日 = 第一個周年日 + 42 天。

2. **請求內容為 `null` 時伺服器崩潰（500）**。`POST /api/company-groups` 傳 `null` 會出現 `TypeError: Cannot read properties of null`。請在 `server.js` 的 `parseBody` 統一處理：JSON 內容不是一般物件（`null`、陣列、數字、字串）時回 400「請求內容格式錯誤」。所有路由一併受惠。加測試。

3. **批文有效期重複錄入**。兩地牌已有 `plate_assets.card_expires_on`（批文卡辨識或手動修改的有效期結束日），但 `approval` 規則要求另外在「到期項目」再填一次，兩邊會不一致。探測結果：兩地牌已有 `card_expires_on`，總覽仍顯示「待錄入」。修改方式：
   - `expiry` 規則支援可選參數 `params.field`，指定從對象的哪個欄位取日期。本階段只允許兩地牌的 `cardExpiresOn`（對應 `card_expires_on`）
   - 預設規則 `approval` 改為 `params: { field: 'cardExpiresOn' }`；`db.js` 為既有租戶把 `approval` 規則中 `params_json='{}'` 的更新為此值（不要覆蓋用戶改過的其他值）
   - 兩地牌 facts 加入 `cardExpiresOn`
   - `GET /api/tracked-items` 對這類規則回傳 `readOnly: true`、`source: '批文卡有效期'` 和實際日期；`PUT` 對這類規則回 400「此日期來自批文卡，請在批文卡修改」
   - 管理端到期項目面板把它顯示成唯讀，並註明「來自批文卡」
   - 規則設定畫面顯示「資料來源：批文卡有效期」，該欄不可改
   - 加測試

4. **完成記錄沒有檢查規則是否適用**。內地公司可以被標記「香港 NAR1 已完成」（探測回 200）。`POST /api/rule-completions` 必須檢查規則已啟用，且 `ruleMatches(rule, facts)` 成立，否則回 400。加測試。

5. **車輛車牌可以改成空白**。`PATCH /api/vehicles/:id` 傳 `plate: '  '` 回 200。車牌不可為空。另外這個路由先逐欄 `UPDATE` 再驗證其他欄位，中途失敗會留下改了一半的資料：請先完成全部驗證，再用一條 `UPDATE` 寫入。

6. **公司可以被搬到另一個客戶**。`PATCH /api/companies/:id` 允許改 `customerId`，會讓公司和原客戶的公司組、兩地牌脫節。`PATCH` 時若 `customerId` 與原值不同，回 400。

## 二、管理端介面（必改）
